# Official result updates

Run `npm run update-data` with Node.js 22 or newer. It downloads both Powerball and Oz Lotto CSVs that Lotterywest offers on [its frequency charts page](https://www.lotterywest.wa.gov.au/results/frequency-charts). The download pattern is `https://www.lotterywest.wa.gov.au/api/games/{gameId}/results-csv`: Powerball is `5132`, Oz Lotto is `5130`. The Powerball endpoint was verified on 2026-09-10 and Oz Lotto on 2026-10-20 (93 weekly draws, 7 January 2025 through 13 October 2026). These downloads are website features, not promised versioned developer APIs; changed formats fail validation. Use `npm run update-data -- --game=powerball` or `--game=ozlotto` to update just one game.

Shared game rules and file names live in `games.js`. Powerball starts on 19 April 2018 (draw 1144), with seven main numbers from 1–35 and one Powerball from 1–20. Oz Lotto's current rules began on 17 May 2022, but this dashboard's fixed collection starts on 1 January 2025: its first Tuesday draw is 7 January 2025 (draw 1612). Oz Lotto rows contain seven main and three supplementary numbers from 1–47, with all ten distinct. Earlier CSV rows are skipped before interpreting historical number formats; collection does not roll forward or delete old draws. Main and supplementary groups are sorted independently. Dates and official draw numbers must agree with the game's weekly Thursday or Tuesday sequence. All collected weeks, including the first, must be present. Duplicate dates/numbers, future draws, invalid dates, empty responses, changed headers, stale source data and conflicting saved results stop that game's update. A conflict needs an evidence-based correction; the updater never overwrites it automatically.

Powerball uses `db.js` / `data-status.json`; Oz Lotto uses `db-ozlotto.js` / `data-status-ozlotto.json`. Each previous database is preserved when fetching, parsing, merging or writing fails, and its status records the failure without changing its last successful synchronization. A first import is allowed only after a complete source history passes all checks; failures never leave a partial database. A successful no-change refresh counts as successful verification only when the source is current enough. Updates run independently: failure for one game does not prevent the other game from being attempted, and the command exits nonzero after all attempts if any failed. The website remains usable from saved data when the source is unavailable.

Freshness uses **Australia/Sydney local time**, including daylight saving. Results from a Thursday become required at **12:00 noon on the following Friday**. Before that deadline (including Thursday night and Friday morning), the previous Thursday is still allowed. For example, 3 September results are acceptable on Thursday 10 September 2026 and until 11:59:59 on Friday 11 September; at noon on Friday the source must include 10 September. A source that keeps returning the same old CSV after this deadline is an update error even if it matches the local data; neither the dataset nor `lastSuccessAt` advances.

Oz Lotto uses the same buffer: Tuesday results become required at **12:00 noon on Wednesday** in Sydney. Before that time the previous Tuesday is allowed. For example, 13 October 2026 remains acceptable until Wednesday 21 October at 11:59:59 AEDT; at noon the source must include 20 October. The UTC deadline shifts with Sydney daylight saving.

`npm run validate` checks both saved datasets and their status agreement. `npm test` includes CSV parsing, game-specific date/range validation, gaps, conflicts, repeated updates, first import, Wednesday/Friday deadlines across daylight saving, rollback and failure isolation. Tests use local fixtures and never access the network. `npm run build` stages both databases and status files in `_site/` and checks they are present.

The workflow runs daily at **14:15 UTC** and can be run manually. It also validates pushes and pull requests. After an automatic/manual synchronization it validates, tests and commits only the four database/status files. The same workflow uploads and deploys the current static artifact, so commits made using `GITHUB_TOKEN` do not need to trigger another workflow. Failed synchronizations publish each failed game's retained valid dataset with its failure status, alongside any successful update to the other game, and mark a separate job failed for GitHub Actions notifications. Other validation failures stop publication.

Before the first hosted run, configure repository Settings → Pages → Source to **GitHub Actions**, and allow workflows to write repository contents. The workflow targets the repository's existing `master` branch. Creating these files locally does not activate Actions or deploy anything; they must first be pushed by the repository owner.

The Lott's actual result-details client exposes `latestresults` and `results/search/drawrange`, but the direct data request returned Access Denied during verification. This updater therefore uses Lotterywest's public CSV rather than relying on that unverified access path. No Lottolyzer fetching dependency is added.
